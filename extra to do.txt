## Core behavior

A region may optionally list one or more full-area blueprint candidates.

The first candidate whose conditions are allowed should replace the region’s normal procedural physical map generation.

If:

* no blueprint list exists
* the list is empty
* a referenced blueprint does not exist
* no candidate condition matches
* a candidate is invalid and cannot safely be used

then the game must use the current procedural generation path.

The existing procedural configuration must remain the implicit default and fallback.

Do not require this:

```js
{ type: "procedural" }
```

Do not require existing regions to wrap their current procedural configuration in a new property.

Do not convert all current regions.

The intended region configuration should be as simple as:

```js
region({
  id: "lookout-post",

  blueprints: [
    {
      id: "lookout_post_rebuilt",
      questCompleted: "clear_and_repair_the_lookout_post",
    },
    {
      id: "lookout_post_under_attack",
      cityStat: {
        cityThreat: { gte: 50 },
      },
    },
  ],

  // Existing procedural configuration remains unchanged.
  tileset: { /* existing config */ },
  objects: [/* existing config */],
  foliageSet: [/* existing config */],
  mobs: [/* existing config */],
  prefabRules: { /* existing config */ },
});
```

Resolution semantics:

1. Evaluate entries from top to bottom.
2. Use the existing `worldEntryAllowed` condition system.
3. The first allowed valid blueprint wins.
4. If none wins, call the old procedural generator through its normal path.
5. Regions with no `blueprints` property must behave exactly as before.

Do not add an implicit unconditional blueprint.

Order is intentional and must be documented and tested.

## Blueprint selection

Create a pure function conceptually similar to:

```js
resolveRegionBlueprint(regionConfig, worldState, context)
```

It should:

* accept missing or malformed lists safely
* evaluate candidates in order
* use `worldEntryAllowed`
* return the selected normalized blueprint plus useful diagnostics
* distinguish:

  * no candidates
  * no condition match
  * unknown blueprint
  * invalid blueprint
  * selected blueprint
* allow procedural fallback without throwing in ordinary gameplay
* log a concise development warning for unknown or invalid matched references
* avoid repeated expensive validation during every frame or chunk

Do not silently select a later blueprint after an earlier candidate’s conditions match but its blueprint is invalid unless this behavior is explicitly chosen and documented.

Preferred safe behavior:

* If an entry’s conditions do not match, continue.
* If an entry matches but references an invalid or missing blueprint, warn and use procedural fallback for the region.
* Do not unpredictably choose a lower-priority blueprint after a higher-priority state matched.

Cover the chosen behavior with tests.
